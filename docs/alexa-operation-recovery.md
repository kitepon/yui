# Alexa操作とオーデリック照明の復旧

2026年10月4日の実施記録。所有者の裁定に従い、一般公開は進めず、実動作の復旧を優先する。

## 修理と反映済み

- ブリッジの状態通知を全機器の目録として扱い、通知のない登録済み照明を同期で削除する欠陥を再現した。オーデリックの同期へ既存登録を渡し、未通知の照明を「状態未取得」として残すよう修理した。
- キッチン照明の元の登録を前日のバックアップで確認し、結の正規APIでその1台だけを復元した。再同期しても3台が残ることと、公開Webのキッチンに「シーリングライト」「状態未取得」が表示されることをJevで確認した。
- セッションCookie更新時にAlexa認可の転送応答が500になる欠陥を再現した。変更可能なヘッダーを持つ302応答へ直し、Cookieと認可コード・stateを保つ試験を追加した。認証方式と既存Alexa連携の情報は変更していない。
- 変更コミット`19d6e9f`をmainへpushし、`origin/main`への包含を確認して本番へ配備した。イメージは`yuihome:20261004-19d6e9f`。
- focused test 12件、Node全288件、lint、型検査、開発ビルド、本番ビルド・配備が成功した。iPhoneのソースは変更しておらず、再ビルドしていない。

## 操作の確認範囲

結の機器操作記録には、15時03分のテレビ操作以降、新しいAlexa操作が無い。現在有効な既存認証での公開APIの機器検出は成功し、復元したキッチン照明も応答一覧に含まれる。トークン更新と再リンクは実行していない。

16時33分に、保存状態がONのリビング照明1台へ、結の正規操作APIからONを1回送った。APIは111ミリ秒でHTTP 200を返し、ブリッジにも送信1件の記録が残った。消灯は行っていない。ブリッジの状態通知に変化はなく、実機が動いたことの確認には含めない。

ブリッジは接続・認証成立と2台分の状態を返している。キッチンの新しい状態は届いていない。ブリッジ本体のコードは、原因を確定できていないため変更していない。

## キッチン操作の優先修理

所有者は、他のオーデリック照明は結から動くが、キッチンだけ動かないと報告した。
壁スイッチはONで、付属リモコンからは操作できることも確認した。

最初の登録復元で、状態未取得の照明を`online: false`としていたため、iPhoneの操作ボタンが無効になっていた。
これは復元時の実装の誤りである。状態の未取得と、接続中のブリッジから指令を送れることを分け、
未通知の登録済み照明でもブリッジの`connected`に従うよう修理した。
修正コミット`fca1b5d`をmainへpushし本番へ配備した。再現試験はfalseからtrueへ変わり、規定チェックとNode288試験が成功した。

正規APIで再同期し、キッチンの`online: true`と3台の登録を確認した。
16時46分51秒にキッチンへONを1回送り、正規APIは91ミリ秒でHTTP 200を返した。
ブリッジにもキッチン宛て送信が1件残った。所有者は実機が点かなかったと回答した。

所有者のキッチン電源OFF→5秒→ON後、17時02分59秒の点灯も実機で失敗した。
照明本体は付属リモコンから動くため、照明の故障とは断定していない。

ブリッジの再起動時にOSへ旧Bluetooth接続が残り、再認証が戻らない現象も実測した。
状態を持つ非公開`odelic-bridge`で、SIGTERMを終了処理へ渡し、通信した照明の接続を終了時に閉じるよう修理した。
非公開リポジトリのコミット`fc99eef`をmainへpushし、正本への包含を確認して実機へ導入した。
20試験とPython構文確認が成功し、新しい処理での再起動後に再認証が戻ることを確認した。
配備前のソースは実機の`/tmp/odelic-bridge-before-fc99eef.tar.gz`へ退避した。照明のプロトコルは結のリポジトリへ追加していない。

Bluetooth上の照明接続が3本ある状態で、17時21分の点灯通知の実配信先は1本だけだった。
残る接続では新しいブリッジとの初期通信を確認できていない。宛先は推測で変更していない。
固定初期値と指令通知後の読取値の関係を調べているが、その違いが実機の初期化失敗の原因とは未確定であり、制御処理は変更していない。

Approval Boxの`K-FPN642`へ、所有者はキッチンをOFFにしたと回答した。
OFF中も残っていたオーデリックの接続2本は変わらず、先に切れていた接続がキッチンである可能性はあるが未確定。
`K-U5EJUA`でキッチンをONへ戻すよう案内した。会話と質問フォームでもONへ戻すことを案内しており、回答待ち。
ON直後のBluetooth初期通信を取得し、物理機器と接続の対応、接続時の読取、認証要求を確認する。

広告の標準設定表示と個別広告の違いはBlueZの仕様で確認した。表示に広告中のフラグが無いことだけでは、個別広告が停止したとは判断できないため、広告設定は変更していない。
接続時の出力読取値は、通知後には認証応答や指令へ変わっていることを確認したが、この動作が照明の初期化失敗の原因とはまだ実測で確定できていない。
この仮説に対する制御コードの変更と、予備Bluetoothアダプタへの切替は実行していない。

## AWS認証とAlexaの後続確認

CloudWatchでLambdaの要求と応答を確認するにはAWSコンソールへのログインが必要。
JevによるAWS画面の確認はログイン画面で停止した。1Passwordの公式CLIでは保存済みAWSログイン項目の存在を確認したが、Jev Desktopの画面取得はTIMEOUTになり、ブラウザからの1Password候補表示も進まなかった。秘密の値を表示していない。

Approval Boxの`K-M7D6C2`で、所有者に保存済み1Password項目を使うAWSログインを依頼した。AWSの設定変更や新規APIキーの発行は不要。
所有者がAWSログインを完了し、CloudWatchのロググループとログストリーム一覧まで読み取り確認できた。
所有者の指示に従い、キッチンを結から操作できる状態へ戻すことを先に行う。
その後、CloudWatchで音声操作の要求が届いているか、Lambdaから結への送信先と応答、機器識別子と認証エラーの有無を読み取り確認する。その結果から原因を特定し、必要な所有製品を修理する。

Alexaからの音声操作と照明の実動作は未復旧・未確認であり、完了として扱わない。
